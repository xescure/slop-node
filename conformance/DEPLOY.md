# Deploying the node

This document states what an operator needs to run `slop-node` as a service: the image, its configuration, the database, the network in front of it, and the rules that keep a node off networks it must not vote on. `[Keeta TS] index.js:N` is line N of `client/index.js` in the published `@keetanetwork/keetanet-client` 0.18.7 package.

## 1. The image

`nix build .#image` writes a gzip-compressed docker-archive tarball (`result`) that `docker load` and `podman load` read. It is named `slop-node`, tagged with the hash of its Nix output, and built only from the flake's inputs, so the same commit gives the same image. `nix build .#default` builds the same node as a plain package, `bin/slop-node`, for hosts that run Nix.

| | |
|---|---|
| Entrypoint | `tini -- slop-node` |
| Command | `run`; replace it to run `genesis`, `clear-peers` or `help` |
| User | `slop-node`, UID 10001, GID 10001 |
| Working directory | `/var/lib/slop-node`, mode 0700, owned by that user |
| Port | `8080/tcp`: the API and the peer WebSocket |
| Environment | `KEETANET_LOCAL_NODE_LISTEN_IP=0.0.0.0`, `KEETANET_LOCAL_NODE_LISTEN_PORT=8080`, `SSL_CERT_FILE=/etc/ssl/certs/ca-bundle.crt`, `TZ=UTC`, `TZDIR=/etc/zoneinfo` |
| Labels | `org.opencontainers.image.title`, `.version` (the version `GET /api/node/version` reports), `.source`, `.licenses`, `.description`, and `.revision` when built from a clean checkout |

The image holds the node with Node.js and what Node.js refers to, the CA bundle and the time zone database. It contains no keys and no other secret: every setting comes from the environment at run time. It is not shell-free: Node.js's closure carries bash, grep and some `-dev` outputs (about 17.5 MiB) through its build-configuration strings, none of them on `PATH`.

The node keeps nothing on disk. When `KEETANET_LOCAL_NODE_POSTGRES_URL` is set, the ledger, the statistics and the peer-to-peer state are in Postgres; otherwise they are in memory and lost when the node exits. The log goes to standard output and standard error. No volume needs mounting; the working directory is writable for the node's user only.

`tini` runs as PID 1 and passes every signal to the node. Linux delivers a signal to a PID 1 only if that process handles it. The node handles SIGTERM and SIGINT only from the start of `run` until the first one arrives, then removes its handlers, so that a second signal ends it at once if stopping hangs; as PID 1 it would ignore that second signal, and any signal sent while it starts.

## 2. Configuration

The node reads its settings from the environment only. `slop-node --help`, or `help` as the image's command, lists every variable with its default. A `KEETANET_LOCAL_NODE_` variable that the node does not read is refused as a likely misspelling, as is a `KEETANET_GENESIS_` one by the `genesis` command, and a variable the node reads may not be set to the empty string.

What a deployment usually sets:

| Variable | |
|---|---|
| `KEETANET_LOCAL_NODE_SEED` | The representative's seed. Secret. |
| `KEETANET_INITIAL_TRUSTED_ACCOUNT` | The network's trusted account, a public key. Required on `local`. |
| `KEETANET_LOCAL_NODE_NETWORK` | `local` (network 0, the default), `dev`, `staging`, `test`, `main`, or the numeric ID of one of them. |
| `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE` | `read-write` (default), `no-voting`, `bootstrap-only` or `read-only`. |
| `KEETANET_LOCAL_NODE_POSTGRES_URL` | The node's database. Secret, since it may hold a password. Without it the ledger is in memory and lost on stop. |
| `KEETANET_LOCAL_NODE_ENDPOINT_API`, `KEETANET_LOCAL_NODE_ENDPOINT_P2P` | Where clients and peers reach the node (section 4). |
| `KEETANET_LOCAL_NODE_MANUAL_PEERS` | The peers the node dials, each as another node prints it on its `peer:` line. |
| `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS` | API endpoints the node catches up from without dialing them. |
| `KEETANET_LOCAL_NODE_BOOTSTRAP_MIN_INTERVAL_MS` | The rest, in milliseconds, each representative the node catches up from gets between the end of one request and the start of the next (1000 on Keeta's networks, 0 on `local`; at most 60000). |
| `KEETANET_LOCAL_NODE_MAX_PEER_SOCKETS` | The most sockets open on `/p2p` at once (512). |
| `KEETANET_LOCAL_NODE_MAX_POSTED_MESSAGES` | The most messages posted over HTTP that the node handles at once (256). |
| `KEETANET_LOCAL_NODE_LOG_LEVEL`, `KEETANET_LOCAL_NODE_LOG_FILTER` | What the log records (`INFO`). |

The fee variables and `KEETANET_LOCAL_NODE_PREFER_UPDATES` are described by `--help`. The `KEETANET_GENESIS_` variables are read by the `genesis` command only, so the trusted account's seed never needs to be in a running node's environment.

The values of `KEETANET_LOCAL_NODE_SEED`, `KEETANET_LOCAL_NODE_FEE_SEED`, `KEETANET_LOCAL_NODE_POSTGRES_URL` and `KEETANET_GENESIS_TRUSTED_SEED` are never repeated in an error or on the startup summary.

**Peer limits.** Each socket on `/p2p` is an open file. The default of 512 stays below the 1024 open files a process may have by default on Linux. Raising `KEETANET_LOCAL_NODE_MAX_PEER_SOCKETS` needs a matching open-files limit (`ulimit -n`, `--ulimit nofile=`, `LimitNOFILE=`), with room for API requests, database connections and the node's own dials. Both limits accept a whole number from 1 to 1048576.

## 3. Postgres

- **Version.** PostgreSQL 15 or later: the schema uses `UNIQUE NULLS NOT DISTINCT`, which 15 introduced. The node's tests run against PostgreSQL 18.
- **One database per logical node.** The database holds one representative's ledger, its vote serials and its peers. The processes that serve one representative may share its database. Two representatives never share one, even on the same network.
- **Migrations.** The node creates and upgrades its schema when it opens the database, so its role must be able to create tables there. Every process that migrates takes the advisory lock `pg_advisory_lock(7738703085231170663)` first, so processes starting together apply each migration exactly once. A database that a newer build has migrated is refused, so a node cannot be rolled back past a schema change.
- **Clock.** No statement reads the database's clock; every stored moment comes from the node's.
- **URL.** `postgresql://user:password@host:5432/database`, or with a Unix socket directory as the host, written with `%2F` for each `/`: `postgresql://user@%2Frun%2Fpostgresql/database`.

## 4. Addresses and the proxy

- **Listening.** The image listens on `0.0.0.0:8080`. A node that listens on every interface (`0.0.0.0` or `::`) cannot tell which address peers reach it at, so it refuses to start unless both `KEETANET_LOCAL_NODE_ENDPOINT_API` and `KEETANET_LOCAL_NODE_ENDPOINT_P2P` are set.
- **One port.** The node serves its API below the path of its API endpoint (`/api` for `https://node.example/api`), and peers on `/p2p` of the same server. The P2P endpoint must be a `ws://` or `wss://` URL whose path is `/p2p`; a P2P endpoint on another path or port is not served.
- **A proxy in front** must:
  - pass the API endpoint's path through unchanged;
  - forward WebSocket upgrades on `/p2p`, and frames of up to 16 MiB, the largest a peer sends [Keeta TS] index.js:71812;
  - accept `POST <api>/p2p/message` bodies of at least 32 MiB, the largest the node accepts.
- **Stable addresses.** A node's `peer:` line carries its signature over its key, its endpoints and how it prefers updates, and peers keep that record. Give each node endpoints that do not change, such as DNS names. A node whose endpoints change must have its new `peer:` line given to every node that names it.
- **Firewall.** `/p2p` and `POST <api>/p2p/message` take any representative's greeting without authentication, and a greeting makes the sender a peer that the node sends staples to and remembers. Allow them only from the hosts of the node's own network.

## 5. Safety rules

The node enforces these at start, before it serves anything:

- On `main` and `test`, the public networks, the node may only follow the ledger: `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE` must be `read-only` or `bootstrap-only`.
- On any network of Keeta's (`dev` and `staging` as well), a node in a voting mode (`read-write` or `no-voting`) may have no peers: it refuses `KEETANET_LOCAL_NODE_MANUAL_PEERS`, `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS`, and peers its database remembers. It then serves nothing on `/p2p` and refuses every posted message.
- Voting with peers is therefore possible on network 0 only, the operator's own network.
- `genesis` is refused on `main` and `test`, and in memory.

## 6. Running

- **Stopping.** On SIGTERM or SIGINT the node stops bootstrapping, closes the peer sockets, waits for the requests in flight, waits up to 5 s for the messages peers delivered, closes its database connections and exits with status 0. Give it a stop timeout of at least 20 s before the runtime kills it: `docker stop -t 20` or `--stop-timeout 20`, `stop_grace_period: 20s` in Compose, `TimeoutStopSec=20` in systemd. Kubernetes' default grace period, 30 s, is enough.
- **Clocks.** Keep every host's clock synchronized with NTP. A vote may be stamped at most 60 s ahead of the clock that reads it [Keeta TS] index.js:80373-80375, and the node's catch-up from its peers allows their clocks to differ from its own by up to 5 minutes.
- **`clear-peers`.** The peers a node remembers belong to the network and mode it ran in. After changing `KEETANET_LOCAL_NODE_NETWORK` or `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE`, stop the node and run `clear-peers` once with its new environment, for example `docker run --rm --env-file node.env slop-node:<tag> clear-peers`. It forgets every remembered peer and keeps the ledger and the statistics. A node in a voting mode on one of Keeta's networks refuses to start while its database remembers peers, and its error names this command.
- **Startup.** Once it serves, the node prints a summary: its version, its representative, network, write mode and storage, and the lines `api:` and `peer:`. `GET <api>/node/version` answers once it serves.
- **Exit status.** 0 after a signal, 1 when the node refuses its configuration or fails, 2 for a command line it does not understand.
- **Background failures.** An error in work the node does in the background while it serves, such as recording a peer in Postgres, is logged at `ERROR` with an error ID and does not stop the node, so watch the log for them; one while the node starts or stops still ends it with status 1.

## 7. A devnet on network 0

An outline for a network of several representatives that only the operator runs.

1. **Keys.** Choose a seed for the trusted account and one seed per representative, 64 hexadecimal digits each. The trusted seed is needed only for genesis. Every node is given the trusted account's public key as `KEETANET_INITIAL_TRUSTED_ACCOUNT`.
2. **Databases.** Create one empty database per node.
3. **Genesis, once.** Run `genesis` against the first node's database, with that node's environment and `KEETANET_GENESIS_TRUSTED_SEED`, `KEETANET_GENESIS_SUPPLY` and optionally `KEETANET_GENESIS_DELEGATE_TO`, which is the first node's representative unless set. The supply's voting weight is delegated to that one representative. The command prints the genesis staple's hash and the network address.
4. **Start every node** with `KEETANET_LOCAL_NODE_NETWORK=local`, `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE=read-write`, its own seed, database and stable endpoints, behind a firewall that admits only the other nodes to the P2P surface. Collect each node's `peer:` line. `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS` is not needed: the manual peers of the next step are always sources a node catches up from, so a node without genesis fetches it from them once restarted. Only a representative that the node merely heard of through its peers must hold a hundredth of the voting weight on the node's own ledger to be one, and a node without genesis knows no weight.
5. **Peers.** Set `KEETANET_LOCAL_NODE_MANUAL_PEERS` on every node to the other nodes' `peer:` lines, and restart them.
6. **Genesis first.** Before publishing anything, wait until every node holds genesis: `GET <api>/node/ledger/account/<network address>/head` answers a `block` other than `null` on every node. Do the same after each staple that changes voting weight, such as a delegation, checking `GET <api>/node/ledger/block/<hash>` on every node, before publishing the next transaction.
7. **Publish** to any node's `POST <api>/node/publish`.
8. **Recovering with fees.** When the representatives charge fees, the client's `UserClient.recover` adds the fee block their votes ask for only when it is given `generateFeeBlock`, and fails with `Votes require fees but generateFeeBlock was not defined` otherwise ([Keeta TS] index.js:59408-59417, 60856-60858). `UserClient.send` recovers the same way after `LEDGER_SUCCESSOR_VOTE_EXISTS` (60644-60653). Pass a generator, such as one returning `initBuilder().computeFeeBlock(staple)`.
9. **One send at a time per account.** After a send, wait until the staple is on every representative before sending again from the same account. A representative asked to vote on a block whose previous block it has not received refuses at once ([Keeta TS] index.js:69266, 69274), and the client's head re-sync recovers only when the heads differ (59445-59473, 59636-59650).

## 8. Following the main network

`utils/follower` runs the node as a follower of the main network on the operator's machine. It needs Node.js and the PostgreSQL server binaries, which `devenv shell` provides.

- **Read-only.** The node runs on `main` in `bootstrap-only` mode: it votes on nothing [Keeta TS] index.js:70172-70174, and adds only the staples it bootstraps, refusing any publish [Keeta TS] index.js:69363-69370. It has no manual peers and listens on `127.0.0.1` only, so it dials no representative and none can reach it. Its key, made once and kept in the directory with mode 0600, signs nothing. Before it starts the node, the tool checks the node's configuration as the node reads it, and refuses any other network, write mode, address, peer or source.
- **Sources.** It bootstraps from the API endpoints of the main network's four representatives, `https://rep1.main.network.api.keeta.com/api` to `rep4`, as the client's configuration of the network names them, and trusts that configuration's initial trusted account, which the node takes as its default on `main` [Keeta TS] index.js:61375-61395.
- **Pacing.** Requests to each representative go one at a time, each at least `KEETANET_LOCAL_NODE_BOOTSTRAP_MIN_INTERVAL_MS` after the previous one ended: 1000 ms unless `--min-interval-ms` says otherwise. A representative answers a page with as many staples as it gathers within its time for the request [Keeta TS] index.js:69639-69647, on the main network about 140 staples, or 1 MiB, in about 3 s, so the follower keeps well under one request in flight per representative. Each update's passes over a representative stop after two minutes or 2000 requests. While a pass stops there, the representative is still ahead and the next update begins at once, its requests paced the same; otherwise the next update begins a minute after the last ended.
- **Directory.** Everything is kept in one directory, `~/.local/share/slop-node-follower` unless `--directory` says otherwise, never under a temporary directory: the seed, the Postgres cluster (`postgres/`, its socket in `run/`, no TCP listener), the settings `up` was given (`follower.json`), and the logs (`node.log`, `postgres.log`). The cluster runs with 1 GiB of shared buffers, about 1.3 GiB of memory in all: a catch-up writes each staple into the history of every account it touches, hundreds on the main network, onto index pages spread over gigabytes, which a small pool reads, evicts and writes again many times. Checkpoints come at most every 30 minutes or 4 GiB of write-ahead log, and the whole pages logged after each are compressed with lz4. Commits do not wait for the disk (`synchronous_commit = off`). A crash may lose the last commits, but only the last: the write-ahead log brings the database back to a consistent state as of an earlier commit. The catch-up cursors and the retry queue are kept in the same database, so a cursor never survives the staples it moved past, and those staples are fetched again. `pg_stat_statements` and I/O timing are on, and `up` creates the extension's view in the database, so the node's queries can be profiled against the follower's ledger. These settings are the follower's; a node's own Postgres is configured by its operator (section 3). The node's heap is limited to 768 MiB unless `--max-heap-mb` says otherwise: its live heap stays about 150 MiB, and V8 lets garbage build up toward the limit before it collects it, which the node's resident memory follows.
- **Commands.** `up` makes the cluster and the seed the first time, starts Postgres and the node in the background, where they outlive the terminal, and waits until the node serves `http://127.0.0.1:47380/api` (`--port` to change). `status` prints, as JSON, the staples held and the newest staple's time, each representative's catch-up cursor, where the first completed pass reached, the ranges read while far behind and where each reached, the staples queued for retry by refusal code, the totals of the bootstrap passes the log records, the node's statistics and ledger checksum, the memory of the node and of Postgres, and the database's size. `logs` prints the end of the node's log, or with `--postgres` the database's, and follows it with `--follow`. `down` stops the node, saying how long it took, then Postgres; a node still running 30 s after SIGTERM is killed. `reset-cursors`, with the node down, forgets where the node reached on each representative, where the first completed pass reached, the ranges, and the staples queued for retry, and keeps the ledger: the next `up` reads the history again from the beginning, and finds held every staple the ledger holds.
- **Catch-up.** A follower starting from nothing reads the ledger from one representative at a time until a pass over one of them completes, so it downloads the history once; it then reads every representative, each from where that pass completed, on every update. Once the history it lacks, from the furthest it reached on any representative up to six minutes ago, spans more than a day, it splits that history into one range per representative instead, and reads the ranges side by side, each representative paced as above, so that the history is still downloaded about once, in about a quarter of the time. Each range starts 61 s before the one before ends. A representative that takes a range on starts 61 s before where the last one reached in it. A representative whose passes over a range fail three times in a row leaves it to another, and reads none for 30 minutes. A representative whose range is read takes on half of what is left of the range with the most left. The ranges and where each reached are kept in the database, and the next `up` resumes them. The catch-up is complete only once every range is read; every representative then goes on from where the ranges end, and the first deep re-scan of the representative the follower had reached furthest on reads the ranges again. Passes over ranges after the earliest fill at most half the retry queue, and wait while it is that full. A range read ahead of the earliest brings many staples that extend blocks the node does not hold yet; the ledger keeps them deferred until those blocks arrive (`schema/CONTRACT.md`, section 2.6). After each update the node runs the ledger's garbage collection for up to five slices of 2 s, which applies the deferred staples whose blocks have arrived. It names the staples it holds to a representative by the bytes it received them as, which are the bytes the representatives hold, so that none is sent again (`schema/CONTRACT.md`, section 1). It logs each pass that adds or queues staples or reaches its bound. Expect the first catch-up to take hours.
- **Out-of-order history.** A representative serves its history in the order its votes were made (`schema/CONTRACT.md`, D8), which is not causal: on the main network the genesis staple comes fifth, after staples whose voters only it gives weight [Keeta TS] index.js:69397-69400, 69740-69752. A staple the ledger refuses is kept in a queue in the database, at most 1000 staples or 16 MiB, and offered again after each page that adds a staple and at the end of each pass, until the ledger accepts it or holds its blocks; the passes move on meanwhile. A pass from where the last one reached fills at most nine tenths of the queue; one that is sent one more refused staple then fails before it moves past it, and the next update reads it again and begins a deep re-scan of the representative at once, which may fill the rest of the queue and reads again any staple the queued ones need that an earlier pass missed. A staple still refused an hour after it was queued is logged once, as a warning: `bootstrap: staple refused for <minutes> min: <code> (staple <blocks hash>)`. It stays queued, and means the follower's ledger diverges from the network's on that staple.
- **How a representative lists its staples.** A pass moves its start on only as far as a page is shown to have read [Keeta TS] index.js:69633-69702. A page as long as the longest the representative has answered may have been cut by a limit of its own, and counts for less, so a representative that answers pages of one length is read more slowly. A representative found to key votes more than a second after they were made is logged once, as a warning naming the staple that showed it, and is then read by what holds for any later key. A pass that names 20000 staples from one moment without a page shown to read past it ends there, and a second pass that ends at the same moment is logged as a warning. A pass names to a representative at most 128 of the staples it holds ahead of where it asks from: a representative runs out of time only once it has a staple to send [Keeta TS] index.js:69641-69647, and one asked to leave out too many answers 504 from its gateway. A representative tests every staple it reads against the filter, so one 504s on a filtered request where an unfiltered one is answered at once. Each 504, or request not answered within the timeout, fails the pass and halves that number for the representative, down to 8; each pass it does not give up on adds 8 back. One that gives up with the number at 8 is asked again with no filter, and so on until a pass over it completes; a pass without a filter is sent again every staple it reads, and completes once the representative has applied staples past its horizon. Naming fewer, or nothing, costs only staples sent again.
- **Parity.** `utils/parity`, run beside an up follower, compares it with the four representatives and records every comparison in `parity.jsonl` in the follower's directory. It reads from the representatives with GET requests only, each representative at least 1 s after the previous request ended, and only one parity command runs at a time in a directory (`parity.lock`). `checksum` first checks the follower's stored ledger checksum against the XOR of the hashes of the blocks of its main ledger, both read from its database in one view after a request to its API has had it write its statistics. They pass when equal, or when they differ by the blocks of some of the 32 staples committed last (not written yet), or by those of one run of at most 1,000 staples committed one after another (statistics lost at a stop that did not write them, `API.md`, Differences); any other difference fails. It then reads the follower's block count and checksum, then each representative's, waits 10 s (`--gap-ms`), and reads each again. Once a bootstrap pass of the follower has completed, its block count must be within 100 blocks of each representative's, widened by how far the representatives count apart and by what either side added between its two readings. The representatives' checksums are recorded for information only: each is a statistic of its own node (`API.md`, Differences). `sweep` walks the accounts the follower's database names, from where the last sweep stopped (`parity-sweep.json`), `--accounts` of them (100), and compares `GET /api/node/ledger/account/{account}` on the follower with one representative, each account with the next representative in turn. An account counts only when the representative's newest staple of it has no vote from within an hour before where the follower holds every staple: then the follower holds every staple of it, and the whole state must agree, head included. The follower is read before and after the representative, and an account it changed in between is skipped as moving; an account the follower holds a staple of from that hour on is skipped without a request. `api-diff` sends the same GET requests to the follower and to a representative, `--samples` of each stratum (50), and compares the answers once the fields `API.md` names as differing between nodes holding the same ledger are normalized: an internal failure's error ID, and a history entry's time and its staple's compression. The strata are quiet accounts of each kind that differs most from a plain account's (tokens, storage accounts, multisig accounts, accounts with certificates, and accounts with permissions as principal or entity), blocks carrying each type of operation, and the edge-case staples (`conformance/mainnet/edge-cases.jsonl.gz`) the follower holds. Every GET route of `api/openapi.json` is sampled except those whose answer describes the node that serves it, the statistics-clearing route, the representatives' weights, which move with any delegating account, and the ledger's history, which each node orders by its own vote. Requests are drawn from the follower's database within its reach, in an order `--seed` fixes (the time of the run), and each counts only when every account its answer reads, the entities a principal's permissions name included, is quiet on both sides as for the sweep. The report bounds each stratum's rate of divergence by the rule of three over its distinct requests, each counted by its latest comparison, and lists the kinds of answer the capture set (`API.md`) holds none of: a route with its status and error code, the kind of account an answer is about, and each type of operation it serves. `shadow` replays the follower's history, read from its database from the first staple to an hour before its reach, into an offline representative ledger that votes nowhere, kept in a PostgreSQL cluster started for the run and removed after it (`--storage memory` keeps it in memory, which holds only a short history), and before each of the last `--window` staples (1,000) is added, asks that ledger to vote on its blocks with the clock at the staple's moment, as the mainnet head's replay does. A refusal must be explained by one of the classified differences between 0.18.4 and 0.18.7 (`MAINNET.md`, section 6); any other refusal, or a staple of the window the replay cannot apply, fails. `make parity` (`utils/parity report`) checks the checksum, compares a sweep of 16 accounts and an API diff of 2 requests of each stratum (`--api-samples`), then prints a JSON report of each signal's verdict (`pass`, `fail` or `not-comparable-yet`), its counts, its confidence bound and its first divergence, the shadow votes' from the latest `shadow` run, and exits 1 when a signal fails.
