# Deploying the node

This document states what an operator needs to run `slop-node` as a service: the image, its configuration, the database, the network in front of it, and the rules that keep a node off networks it must not vote on. `[Keeta TS] index.js:N` is line N of `client/index.js` in the published `@keetanetwork/keetanet-client` 0.18.7 package.

## 1. The image

`nix build .#image` writes a gzip-compressed docker-archive tarball (`result`) that `docker load` and `podman load` read. It is named `slop-node`, tagged with the hash of its Nix output, and built only from the flake's inputs, so the same commit gives the same image. `nix build .#default` builds the same node as a plain package, `bin/slop-node`, for hosts that run Nix.

| | |
|---|---|
| Entrypoint | `tini -- slop-node` |
| Command | `run`; replace it to run `genesis`, `clear-peers` or `help` |
| User | `slop-node`, UID 10001, GID 10001 |
| Working directory | `/var/lib/slop-node`, mode 0700, owned by that user |
| Port | `8080/tcp`: the API and the peer WebSocket |
| Environment | `KEETANET_LOCAL_NODE_LISTEN_IP=0.0.0.0`, `KEETANET_LOCAL_NODE_LISTEN_PORT=8080`, `SSL_CERT_FILE=/etc/ssl/certs/ca-bundle.crt`, `TZ=UTC`, `TZDIR=/etc/zoneinfo` |
| Labels | `org.opencontainers.image.title`, `.version` (the version `GET /api/node/version` reports), `.source`, `.licenses`, `.description`, and `.revision` when built from a clean checkout |

The image holds the node with Node.js and what Node.js refers to, the CA bundle and the time zone database. It contains no keys and no other secret: every setting comes from the environment at run time. It is not shell-free: Node.js's closure carries bash, grep and some `-dev` outputs (about 17.5 MiB) through its build-configuration strings, none of them on `PATH`.

The node keeps nothing on disk. When `KEETANET_LOCAL_NODE_POSTGRES_URL` is set, the ledger, the statistics and the peer-to-peer state are in Postgres; otherwise they are in memory and lost when the node exits. The log goes to standard output and standard error. No volume needs mounting; the working directory is writable for the node's user only.

`tini` runs as PID 1 and passes every signal to the node. Linux delivers a signal to a PID 1 only if that process handles it. The node handles SIGTERM and SIGINT only from the start of `run` until the first one arrives, then removes its handlers, so that a second signal ends it at once if stopping hangs; as PID 1 it would ignore that second signal, and any signal sent while it starts.

## 2. Configuration

The node reads its settings from the environment only. `slop-node --help`, or `help` as the image's command, lists every variable with its default. A `KEETANET_LOCAL_NODE_` variable that the node does not read is refused as a likely misspelling, as is a `KEETANET_GENESIS_` one by the `genesis` command, and a variable the node reads may not be set to the empty string.

What a deployment usually sets:

| Variable | |
|---|---|
| `KEETANET_LOCAL_NODE_SEED` | The representative's seed. Secret. |
| `KEETANET_INITIAL_TRUSTED_ACCOUNT` | The network's trusted account, a public key. Required on `local`. |
| `KEETANET_LOCAL_NODE_NETWORK` | `local` (network 0, the default), `dev`, `staging`, `test`, `main`, or the numeric ID of one of them. |
| `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE` | `read-write` (default), `no-voting`, `bootstrap-only` or `read-only`. |
| `KEETANET_LOCAL_NODE_POSTGRES_URL` | The node's database. Secret, since it may hold a password. Without it the ledger is in memory and lost on stop. |
| `KEETANET_LOCAL_NODE_ENDPOINT_API`, `KEETANET_LOCAL_NODE_ENDPOINT_P2P` | Where clients and peers reach the node (section 4). |
| `KEETANET_LOCAL_NODE_MANUAL_PEERS` | The peers the node dials, each as another node prints it on its `peer:` line. |
| `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS` | API endpoints the node catches up from without dialing them. |
| `KEETANET_LOCAL_NODE_BOOTSTRAP_MIN_INTERVAL_MS` | The rest, in milliseconds, each representative the node catches up from gets between the end of one request and the start of the next (1000 on Keeta's networks, 0 on `local`; at most 60000). |
| `KEETANET_LOCAL_NODE_MAX_PEER_SOCKETS` | The most sockets open on `/p2p` at once (512). |
| `KEETANET_LOCAL_NODE_MAX_POSTED_MESSAGES` | The most messages posted over HTTP that the node handles at once (256). |
| `KEETANET_LOCAL_NODE_LOG_LEVEL`, `KEETANET_LOCAL_NODE_LOG_FILTER` | What the log records (`INFO`). |
| `KEETANET_LOCAL_NODE_LOG_FORMAT` | `text` (default), or `json`: each log entry and the startup summary as one object per line, with `level`, `message` and `time`, which Railway reads as a structured log. |

The fee variables and `KEETANET_LOCAL_NODE_PREFER_UPDATES` are described by `--help`. The `KEETANET_GENESIS_` variables are read by the `genesis` command only, so the trusted account's seed never needs to be in a running node's environment.

The values of `KEETANET_LOCAL_NODE_SEED`, `KEETANET_LOCAL_NODE_FEE_SEED`, `KEETANET_LOCAL_NODE_POSTGRES_URL` and `KEETANET_GENESIS_TRUSTED_SEED` are never repeated in an error or on the startup summary.

**Peer limits.** Each socket on `/p2p` is an open file. The default of 512 stays below the 1024 open files a process may have by default on Linux. Raising `KEETANET_LOCAL_NODE_MAX_PEER_SOCKETS` needs a matching open-files limit (`ulimit -n`, `--ulimit nofile=`, `LimitNOFILE=`), with room for API requests, database connections and the node's own dials. Both limits accept a whole number from 1 to 1048576.

## 3. Postgres

- **Version.** PostgreSQL 15 or later: the schema uses `UNIQUE NULLS NOT DISTINCT`, which 15 introduced. The node's tests run against PostgreSQL 18.
- **One database per logical node.** The database holds one representative's ledger, its vote serials and its peers. The processes that serve one representative may share its database. Two representatives never share one, even on the same network.
- **Migrations.** The node creates and upgrades its schema when it opens the database, so its role must be able to create tables there. Every process that migrates takes the advisory lock `pg_advisory_lock(7738703085231170663)` first, so processes starting together apply each migration exactly once. A database that a newer build has migrated is refused, so a node cannot be rolled back past a schema change.
- **Clock.** No statement reads the database's clock; every stored moment comes from the node's.
- **URL.** `postgresql://user:password@host:5432/database`, or with a Unix socket directory as the host, written with `%2F` for each `/`: `postgresql://user@%2Frun%2Fpostgresql/database`.

## 4. Addresses and the proxy

- **Listening.** The image listens on `0.0.0.0:8080`. A node that listens on every interface (`0.0.0.0` or `::`) cannot tell which address peers reach it at, so it refuses to start unless both `KEETANET_LOCAL_NODE_ENDPOINT_API` and `KEETANET_LOCAL_NODE_ENDPOINT_P2P` are set.
- **One port.** The node serves its API below the path of its API endpoint (`/api` for `https://node.example/api`), and peers on `/p2p` of the same server. The P2P endpoint must be a `ws://` or `wss://` URL whose path is `/p2p`; a P2P endpoint on another path or port is not served.
- **A proxy in front** must:
  - pass the API endpoint's path through unchanged;
  - forward WebSocket upgrades on `/p2p`, and frames of up to 16 MiB, the largest a peer sends [Keeta TS] index.js:72960;
  - accept `POST <api>/p2p/message` bodies of at least 32 MiB, the largest the node accepts.
- **Stable addresses.** A node's `peer:` line carries its signature over its key, its endpoints and how it prefers updates, and peers keep that record. Give each node endpoints that do not change, such as DNS names. A node whose endpoints change must have its new `peer:` line given to every node that names it.
- **Firewall.** `/p2p` and `POST <api>/p2p/message` take any representative's greeting without authentication, and a greeting makes the sender a peer that the node sends staples to and remembers. On the operator's own network, allow them only from the hosts of that network.

## 5. Safety rules

The node enforces these at start, before it serves anything. A node in `no-voting` mode neither votes nor quotes: the ledger refuses both in any mode but `read-write` [Keeta TS] index.js:70058-70060, 71208-71210.

- On `main` and `test`, the public networks, the node may not vote: `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE` must be `read-only`, `bootstrap-only` or `no-voting`.
- On any other network of Keeta's (`dev` and `staging`), a node in `read-write` mode may have no peers: it refuses `KEETANET_LOCAL_NODE_MANUAL_PEERS`, `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS`, and peers its database remembers. It then serves nothing on `/p2p` and refuses every posted message.
- On `main` and `test` a node in `read-only` or `bootstrap-only` mode keeps its peer-to-peer surface closed: it refuses `KEETANET_LOCAL_NODE_MANUAL_PEERS` and peers its database remembers, serves nothing on `/p2p`, and refuses every posted message unread, so it never greets a peer back nor dials one. It reads those networks only by its bootstrap, over HTTP, from `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS`.
- A node in `no-voting` mode is open to peers on every network, `main` and `test` included: it takes manual, bootstrap and remembered peers, serves `/p2p` and handles posted messages. It adds the staples its peers and clients send it, and passes on only those it adds [Keeta TS] index.js:70399-70409, 72512-72536, 72543-72598.
- Voting with peers is therefore possible on network 0 only, the operator's own network.
- `genesis` is refused on `main` and `test`, and in memory.

## 6. Running

- **Stopping.** On SIGTERM or SIGINT the node stops bootstrapping, closes the peer sockets, waits for the requests in flight, waits up to 5 s for the messages peers delivered, closes its database connections and exits with status 0. Give it a stop timeout of at least 20 s before the runtime kills it: `docker stop -t 20` or `--stop-timeout 20`, `stop_grace_period: 20s` in Compose, `TimeoutStopSec=20` in systemd. Kubernetes' default grace period, 30 s, is enough.
- **Clocks.** Keep every host's clock synchronized with NTP. A vote may be stamped at most 60 s ahead of the clock that reads it [Keeta TS] index.js:81525-81527, and the node's catch-up from its peers allows their clocks to differ from its own by up to 5 minutes.
- **`clear-peers`.** The peers a node remembers belong to the network and mode it ran in. After changing `KEETANET_LOCAL_NODE_NETWORK` or `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE`, stop the node and run `clear-peers` once with its new environment, for example `docker run --rm --env-file node.env slop-node:<tag> clear-peers`. It forgets every remembered peer and keeps the ledger and the statistics. A node whose network is closed to its peer-to-peer surface (section 5) refuses to start while its database remembers peers, and its error names this command.
- **`reindex-history`.** Which accounts' history lists a staple is the rule of `schema/CONTRACT.md`, D18. A database whose staples were added by a build with another rule keeps that build's history until it is listed again: stop the node and run `reindex-history` once with its environment. It reads the staples of the ledger in the order they were stored, in batches of 200, each rewritten in a transaction of its own that also records the batch's last staple, and prints the totals after each batch. Stopped and run again, it resumes after the last staple recorded; run again once it has read every staple, it reads only the staples stored since, which the node listed under the rule of its build. It changes nothing else, and a ledger the same build wrote is left as it is.
- **Startup.** Once it serves, the node prints a summary: its version, its representative, network, write mode and storage, and the lines `api:` and `peer:`. `GET <api>/node/version` answers once it serves.
- **Exit status.** 0 after a signal, 1 when the node refuses its configuration or fails, 2 for a command line it does not understand.
- **Background failures.** An error in work the node does in the background while it serves, such as recording a peer in Postgres, is logged at `ERROR` with an error ID and does not stop the node, so watch the log for them; one while the node starts or stops still ends it with status 1.

## 7. A devnet on network 0

An outline for a network of several representatives that only the operator runs.

1. **Keys.** Choose a seed for the trusted account and one seed per representative, 64 hexadecimal digits each. The trusted seed is needed only for genesis. Every node is given the trusted account's public key as `KEETANET_INITIAL_TRUSTED_ACCOUNT`.
2. **Databases.** Create one empty database per node.
3. **Genesis, once.** Run `genesis` against the first node's database, with that node's environment and `KEETANET_GENESIS_TRUSTED_SEED`, `KEETANET_GENESIS_SUPPLY` and optionally `KEETANET_GENESIS_DELEGATE_TO`, which is the first node's representative unless set. The supply's voting weight is delegated to that one representative. The command prints the genesis staple's hash and the network address.
4. **Start every node** with `KEETANET_LOCAL_NODE_NETWORK=local`, `KEETANET_LOCAL_NODE_LEDGER_WRITE_MODE=read-write`, its own seed, database and stable endpoints, behind a firewall that admits only the other nodes to the P2P surface. Collect each node's `peer:` line. `KEETANET_LOCAL_NODE_BOOTSTRAP_PEERS` is not needed: the manual peers of the next step are always sources a node catches up from, so a node without genesis fetches it from them once restarted. Only a representative that the node merely heard of through its peers must hold a hundredth of the voting weight on the node's own ledger to be one, and a node without genesis knows no weight.
5. **Peers.** Set `KEETANET_LOCAL_NODE_MANUAL_PEERS` on every node to the other nodes' `peer:` lines, and restart them.
6. **Genesis first.** Before publishing anything, wait until every node holds genesis: `GET <api>/node/ledger/account/<network address>/head` answers a `block` other than `null` on every node. Do the same after each staple that changes voting weight, such as a delegation, checking `GET <api>/node/ledger/block/<hash>` on every node, before publishing the next transaction.
7. **Publish** to any node's `POST <api>/node/publish`.
8. **Recovering with fees.** When the representatives charge fees, the client's `UserClient.recover` adds the fee block their votes ask for only when it is given `generateFeeBlock`, and fails with `Votes require fees but generateFeeBlock was not defined` otherwise ([Keeta TS] index.js:60400-60409, 61846-61848). `UserClient.send` recovers the same way after `LEDGER_SUCCESSOR_VOTE_EXISTS` (60644-60653). Pass a generator, such as one returning `initBuilder().computeFeeBlock(staple)`.
9. **One send at a time per account.** After a send, wait until the staple is on every representative before sending again from the same account. A representative asked to vote on a block whose previous block it has not received refuses at once ([Keeta TS] index.js:70302, 70310), and the client's head re-sync recovers only when the heads differ (59445-59473, 59636-59650).

## 8. Following the main network

`utils/follower` runs the node as a follower of the main network on the operator's machine. It needs Node.js and the PostgreSQL server binaries, which `devenv shell` provides.

- **Read-only.** The node runs on `main` in `bootstrap-only` mode: it votes on nothing [Keeta TS] index.js:71208-71210, and adds only the staples it bootstraps, refusing any publish [Keeta TS] index.js:70399-70406. In that mode it has no peer-to-peer surface on `main` (section 5), and the tool refuses any other, `no-voting` included, which would open it to peers: it serves nothing on `/p2p`, refuses posted messages, and starts with no peer remembered, so it greets and dials no one; it listens on `127.0.0.1` only, so no other host reaches its API. Its key, made once and kept in the directory with mode 0600, signs nothing. Before it starts the node, the tool checks the node's configuration as the node reads it, and refuses any other network, write mode, address, peer or source.
- **Sources.** It bootstraps from the API endpoints of the main network's four representatives, `https://rep1.main.network.api.keeta.com/api` to `rep4`, as the client's configuration of the network names them, and trusts that configuration's initial trusted account, which the node takes as its default on `main` [Keeta TS] index.js:62365-62385.
- **Pacing.** Requests to each representative go one at a time, each at least `KEETANET_LOCAL_NODE_BOOTSTRAP_MIN_INTERVAL_MS` after the previous one ended: 1000 ms unless `--min-interval-ms` says otherwise. A representative answers a page with as many staples as it gathers within its time for the request [Keeta TS] index.js:70675-70683, on the main network about 140 staples, or 1 MiB, in about 3 s, so the follower keeps well under one request in flight per representative. Each update's passes over a representative stop after two minutes or 2000 requests. While a pass stops there, the representative is still ahead and the next update begins at once, its requests paced the same; otherwise the next update begins a minute after the last ended.
- **Directory.** Everything is kept in one directory, `~/.local/share/slop-node-follower` unless `--directory` says otherwise, never under a temporary directory: the seed, the Postgres cluster (`postgres/`, its socket in `run/`, no TCP listener), the settings `up` was given (`follower.json`), and the logs (`node.log`, `postgres.log`). The cluster runs with 3 GiB of shared buffers, about 3.3 GiB of memory in all: a catch-up writes each staple into the history of every account it touches, hundreds on the main network, onto index pages spread over gigabytes, which a small pool reads, evicts and writes again many times. Checkpoints come at most every 30 minutes or 4 GiB of write-ahead log, and the whole pages logged after each are compressed with lz4. Commits do not wait for the disk (`synchronous_commit = off`). A crash may lose the last commits, but only the last: the write-ahead log brings the database back to a consistent state as of an earlier commit. The catch-up cursors and the retry queue are kept in the same database, so a cursor never survives the staples it moved past, and those staples are fetched again. `pg_stat_statements` and I/O timing are on, and `up` creates the extension's view in the database, so the node's queries can be profiled against the follower's ledger. Each transaction may hold 1,024 predicate locks (`max_pred_locks_per_transaction`): every transaction is serializable, and the shadow votes' offline ledger in the same cluster ran the default 64 out beside the node. These settings are the follower's; a node's own Postgres is configured by its operator (section 3). The node's heap is limited to 768 MiB unless `--max-heap-mb` says otherwise: its live heap stays about 150 MiB, and V8 lets garbage build up toward the limit before it collects it, which the node's resident memory follows.
- **Commands.** `up` makes the cluster and the seed the first time, starts Postgres and the node in the background, where they outlive the terminal, and waits until the node serves `http://127.0.0.1:47380/api` (`--port` to change). `status` prints, as JSON, whether the follower is caught up as the parity tools judge it (a pass completed, and its ledger applied all it read: nothing staged, queued for retry, or deferred before that pass's horizon behind a block it lacks), the staples held and the newest staple's time, the deferred staples stranded so, whether the retry queue is full (`retryQueueFull`), which stalls the adding of what was staged, as the node's log then says, each representative's catch-up cursor, where the first completed pass reached, the ranges read while far behind and where each reached, the staples queued for retry by refusal code, the staples staged and not added yet with their size and earliest vote, the totals of the bootstrap passes the log records, the node's statistics and ledger checksum, the memory of the node and of Postgres, and the database's size. `logs` prints the end of the node's log, or with `--postgres` the database's, and follows it with `--follow`. `down` stops the node, saying how long it took, then Postgres; a node still running 30 s after SIGTERM is killed, and Postgres 10 minutes after its fast shutdown began, which writes every dirty page of its pool first. `reset-cursors`, with the node down, forgets where the node reached on each representative, where the first completed pass reached, the ranges, and the staples queued for retry, and keeps the ledger: the next `up` reads the history again from the beginning, and finds held every staple the ledger holds. `reindex-history`, with the node down, lists each staple the ledger holds in the history of the accounts this build lists it under, as the node's own `reindex-history` does (section 6). `snapshot` copies the follower's database as it stands into `follower_snapshot_<UTC time>` in its cluster, file by file; a copy needs no session on the database, so it stops the node for the copy, keeping Postgres and its buffer pool running, and starts the node again with the settings it last ran with. `restage`, with the node down, stages every staple the ledger holds, has deferred or queued for retry, as the bytes it holds, in a new database, with where the node reached on each representative and the ranges, and gives that database the follower's database's name, keeping the one before as `follower_before_restage_<UTC time>`; it takes the name only once the stage holds as many staples as were read. The next `up` adds the staged staples again in the order of their votes, and reads from the representatives only what was not read. It is how a ledger that added history out of that order is rebuilt without reading it again.
- **Catch-up.** A follower starting from nothing reads the ledger from one representative at a time until a pass over one of them completes, so it downloads the history once; it then reads every representative, each from where that pass completed, on every update. Once the history it lacks, from the furthest it reached on any representative up to six minutes ago, spans more than a day, it splits that history into one range per representative instead, and reads the ranges side by side, each representative paced as above, so that the history is still downloaded about once, in about a quarter of the time. Each range starts 60.1 s before the one before ends. A representative that takes a range on starts 60.1 s before where the last one reached in it. A representative whose passes over a range fail three times in a row leaves it to another, and reads none for 30 minutes. A representative whose range is read takes on half of what is left of the range with the most left. The ranges and where each reached are kept in the database, and the next `up` resumes them. The catch-up is complete only once every range is read and every staple read is added; every representative then goes on from where the ranges end, and the first deep re-scan of the representative the follower had reached furthest on reads the ranges again. The passes over the ranges do not add what they read: they stage it in the database (`schema/CONTRACT.md`, section 4.3), and the node adds the staged staples in the order of their earliest votes, those made up to 60.1 s before where the range that reached least has reached, as one pass from the beginning would, since the ledger checks each staple against the voting weight it holds when the staple is added [Keeta TS] index.js:69397-69401, 70776-70795. Once no range is left, it adds every staged staple, and the passes add what they read again. Passes over ranges that start more than a day past where the earliest reached stop before the next staple while the stage holds 4 GiB, and wait until it holds less. The node logs what each update added of the stage, and how much remains staged. A staple whose dependency was voted within the slop after it is refused, queued and added once the dependency is; the ledger keeps a staple that extends a block it does not hold yet deferred until the block arrives (`schema/CONTRACT.md`, section 2.6). After each update the node runs the ledger's garbage collection in slices of 2 s until it reports nothing left, which applies the deferred staples whose blocks have arrived: a chain of one account's staples deferred behind one block is applied whole, a replay window's worth a slice, before the next update adds more, which would otherwise be deferred behind it too. It names the staples it holds to a representative by the bytes it received them as, which are the bytes the representatives hold, so that none is sent again (`schema/CONTRACT.md`, section 1). It logs each pass that adds or queues staples or reaches its bound. Expect the first catch-up to take hours.
- **Out-of-order history.** A representative serves its history in the order its votes were made (`schema/CONTRACT.md`, D8), which is not causal: on the main network the genesis staple comes fifth, after staples whose voters only it gives weight [Keeta TS] index.js:69397-69400, 70776-70788. A staple the ledger refuses is kept in a queue in the database, and in memory as the bytes it came as, at most 1000 staples or 16 MiB, until the ledger accepts it or holds its blocks; the passes move on meanwhile. After each page that adds a staple and at the end of each pass, the queue offers again the staples that are due: one refused for want of voting weight once its voters' weight passes the ledger's check, one refused for anything else once a staple the bootstrap adds lands on an account it names, and any staple once a wait since its last refusal has passed, 30 s after the first and doubling with each refusal up to 30 minutes, so that every queued staple is offered again for as long as it stays queued. A pass from where the last one reached fills at most nine tenths of the queue; one that is sent one more refused staple then fails before it moves past it, and the next update reads it again and begins a deep re-scan of the representative at once, which may fill the rest of the queue and reads again any staple the queued ones need that an earlier pass missed. A staple still refused an hour after it was queued is logged once, as a warning: `bootstrap: staple refused for <minutes> min: <code> (staple <blocks hash>)`. It stays queued, and means the follower's ledger diverges from the network's on that staple.
- **How a representative lists its staples.** A pass moves its start on only as far as a page is shown to have read [Keeta TS] index.js:70669-70738. A page as long as the longest the representative has answered may have been cut by a limit of its own, and counts for less, so a representative that answers pages of one length is read more slowly. A representative found to key votes more than 100 ms after they were made is logged once, as a warning naming the staple that showed it, and is then read by what holds for any later key. A pass that names 20000 staples from one moment without a page shown to read past it ends there, and a second pass that ends at the same moment is logged as a warning. A pass names to a representative at most 128 of the staples it holds ahead of where it asks from: a representative runs out of time only once it has a staple to send [Keeta TS] index.js:70677-70683, and one asked to leave out too many answers 504 from its gateway. A representative tests every staple it reads against the filter, so one 504s on a filtered request where an unfiltered one is answered at once. Each 504, or request not answered within the timeout, fails the pass and halves that number for the representative, down to 8; each pass it does not give up on adds 8 back. One that gives up with the number at 8 is asked again with no filter, and so on until a pass over it completes; a pass without a filter is sent again every staple it reads, and completes once the representative has applied staples past its horizon. Naming fewer, or nothing, costs only staples sent again.
- **Parity.** `utils/parity`, run beside an up follower, compares it with the four representatives and records every comparison in `parity.jsonl` in the follower's directory. It reads from the representatives with GET requests only, at most 4 in flight to each representative at a time (`--rep-concurrency`), each starting at least `--rep-gap-ms` (0) after the one before it to that representative, and only one parity command runs at a time in a directory (`parity.lock`), so the pacing holds across the tools. A representative that answers 429, or a server error without the API's error envelope, which a gateway or proxy answers in its place, or three internal failures in a row in the envelope with no error code of the API, as a representative failing under load answers, or whose request fails outright, has its requests in flight halved, down to one, and gets no request for 1 s, doubled with each such answer in a row up to 30 s, or for as long as its `Retry-After` asks; each run of 10 answers without one, and without an internal failure naming no code of the API, lets one more request be in flight again, up to the most allowed. Each backoff is written to the command's standard error, and how often each representative was backed off from when the command ends. The tools read the follower's database through at most 4 read-only sessions, beside the node and the offline ledger of `shadow` in the same cluster. A read that waits past 10 s for a session, runs past the 30 s statement timeout, or finds the cluster out of connections is the cluster's load, not a failure of the read: it is read again after 1 s, doubled up to 30 s, until it succeeds or the command is stopped, but for a read whose statement ran past the timeout ten times in a row, which runs longer than it whatever the load and is given up. A cluster that is not serving, starting or shutting down or with no server behind its socket, fails the command at once while none of its reads has succeeded, as a follower that is not running or a directory that is not its; after one has, it is waited out the same way, as through a restart of the follower, for 15 minutes at most before the read is given up. Each wait is written to standard error with the attempt it was and how long the read has taken, so that a walk neither stops on it nor records it as a comparison, and a read that never succeeds shows. The reads of accounts with a chain, a thousand to a statement when every one is read, have 5 minutes each, and a failure of one page reads again from that page. `checksum` first checks the follower's stored ledger checksum, the one its API serves, which each staple's write folds the staple's checksum into, against the XOR of the hashes of the blocks of its main ledger, both read from its database in one view. They pass only when equal; when they differ, the record names the first staples whose own checksum is not the XOR of their blocks' hashes (`API.md`, Differences). It then reads the follower's block count and checksum, then each representative's, waits 10 s (`--gap-ms`), and reads each again. Once a bootstrap pass of the follower has completed and it has added every staple it staged, its block count must be within 100 blocks of each representative's, widened by what either side added between its two readings and never by how far the representatives count apart; a representative counting more than 100 blocks from the median of those that answered keeps a count of its own and is recorded as not comparable (`representative-outlier`); until then, and while staples the ledger refused wait in its retry queue or staples voted before the pass's horizon wait deferred behind a block it lacks, as for its being caught up, the comparison is recorded as not comparable, with the reason (`no-completed-pass`, `stage-not-empty`, `retry-queued`, `retry-queue-full` for a full queue, which stalls the stage too, `deferred-stranded`), since the follower's ledger stands at an earlier point of the history or lacks staples the representatives hold. Each `checksum` also records what keeps the follower from being caught up once its stage is empty (`held-back`): the staples waiting in its retry queue, with their latest refusal and when they were queued, and the staples deferred before the pass's horizon behind a block the main ledger lacks, with those blocks, a hundred of each at most, the oldest first. The report reads them again as it is made, and, once a pass has completed and while the node runs, fails the checksum on a staple refused for an hour or more, as long as the node waits before it reports one, or one every reading has found stranded for an hour or more, each counted from the later of then and the node's start, as a node that was down retried nothing (the time `up` wrote `node.pid`), naming each staple and why: such a staple keeps the follower from ever being caught up, so every comparison gated on that would otherwise say `not-comparable-yet` for good. One held back for less leaves the checksum `not-comparable-yet`. The representatives' checksums are recorded for information only, as agreeing with the follower's or differing from it: each is a statistic of its own node (`API.md`, Differences), so a difference reads nothing more. `sweep` walks the accounts the follower's database names in two walks side by side, each from where it stopped last (`parity-sweep-chain.json`, `parity-sweep-passive.json`), `--accounts` of each (100), or on to the end of the lap each is on (`--lap`). The chain walk goes over the accounts with a chain on the follower's main ledger, and compares `GET /api/node/ledger/account/{account}` on the follower with one representative, each account with the next representative in turn. An account counts only when the representative's newest staple of it has no vote from within an hour before where the follower holds every staple: then the follower holds every staple of it, and the whole state must agree, head included. The follower is read before and after the representative, and an account it changed in between is skipped as moving; an account the follower holds a staple of from that hour on is not read by its state. An account found moving is compared again at once, twice, and one still moving, as a busy account is on every attempt, or held by the follower from that hour on, is compared by its chain: the representative's chain is read from its head down to the follower's head, at most 2,000 blocks in pages of 200, and the follower's chain is the representative's when its head is a block of it, since each block names the one before it; the blocks above it, which the follower lacks, must all be too recent for the follower to hold, which the oldest decides: a representative votes on a block only within five minutes of its date [Keeta TS] index.js:71221-71232, so one dated more than five minutes before the hour before the follower's reach is one the follower must hold. Such an account is recorded as `compared-chain`, and a chain that disagrees is a divergence like a state that does. A chain comparison checks the account's own chain only, that the follower holds each block of it: neither its balances, its permissions nor its history are compared, so a staple the follower holds but applied wrongly to the state of such an account, an incoming send's credit or a permission another account set, is seen by no signal of the sweep. This is the sweep's limit for every account compared by its chain, which covers each account moving on every attempt and each account the follower holds a staple of from within the hour, whoever's block that staple carries; the checksum cross-check and the block count cover the staples the follower holds, not the state they leave. The report counts these accounts apart (`comparedByChain`), neither among the state matches nor among the samples its confidence bound is over, and `everyAccountCompared` counts them as compared, so a verdict that quotes it quotes `comparedByChain` beside it. `recheck` compares a chain divergence again by the chain. At the end of each lap the chain walk compares by itself each account with a chain it did not walk, one that gained its chain after the walk passed its row, before the lap ends. The passive walk goes over the rest, whose state only other accounts' blocks change, 100 at a time, each hundred with the next representative in turn, as many hundreds in flight to each representative as `--rep-concurrency` allows, and moves its cursor once every hundred of the batch is compared, through `GET /api/node/ledger/accounts/{accounts}`, which takes the accounts as one comma-separated path segment and answers one state for each, in the order asked [Keeta TS] index.js:59562-59574; the representatives and the follower alike answer 431 to a request line beyond about 16 KiB, some 225 accounts. An account the two answer alike matches, as no lag of either side makes unequal states equal, but for one both answer with the same error in place of its state, which is recorded as `error-both` and counts as not compared, so it keeps `everyAccountCompared` false until a later comparison reads a state: `recheck` reads such an account again by itself, and one both sides answer with the same error every time is an artifact of the account, to be explained in `API.md`, Differences, as an error both nodes answer alike; a follower that fails the request, or answers a list that is not one state for each account, has each account compared by itself. An account answered apart is compared by itself as the chain walk compares one, its newest staple, the latest that touched it, standing in for a head, so the difference counts only when that staple has no vote from within the hour before the follower's reach, where the follower holds every staple of the account, and persists when both are read again; otherwise it is skipped as moving and compared again on the next lap. No time passes between the batch and the second reading: the hour the newest staple must predate the follower's reach by is the quiet window, and it is stricter than a wait, since it holds only for an account no staple touched within it. Each batch is recorded with the rows it went over and the accounts it did not compare, and a batch the representative does not answer leaves all of them not compared. An account that diverges in either walk is read again, state and newest staple, from every other representative; a representative whose newest staple of it is from within the hour gives no reading. The divergence is the follower's when the follower disagrees with most of the representatives that gave one, the one compared with among them; it is the own of the representatives that answered apart (`representative-local`, `API.md`, Differences) when at least two answer as the follower, every other value is answered by fewer, and the follower holds what each representative apart holds newest of the account, the staple of its newest history entry or, for a chain, the block at its head, each representative apart then charged with it; for a chain two other representatives must stand at the follower's head, one whose chain runs on past it holding the account at another point; and never for a staple the follower lacks, since another representative may list a different staple first and agree on a state the lacked staple left unchanged; otherwise it is `unresolved`, which fails like a divergence. A divergence left to the representatives apart, or unresolved, also records whether the follower's balances of the account are those its own history leaves it with, the net of every balance change of the staples of that history, read in the order the ledger added them, token by token, as the ledger computes their effects: the balances the follower stores and its history are read in one view of its database, the history's staples by their hashes in one statement and their bytes 200 at a time, and, the stored balances being those of the history, the state its API serves, read while that view holds, and the state compared, by its balances or, for a chain, its head against the head stored, must be the one it stores, or nothing is checked, as the account moved; when the stored balances are not those of the history, the divergence is the follower's whatever the representatives answer, and one left to the representatives apart without a consistent check counts as unresolved, failing the sweep and counted so by `sweep` and `recheck` too, until a later comparison makes one. Every reading is recorded with it. `recheck` compares again, in the same way, each account whose latest comparison diverged or was unresolved, or left the difference to a representative without the check of the follower's balances, or whose latest attempt both sides answered with the same error, with the representative it was compared with. It then compares by itself each account the coverage counts as never compared, as its walk would (a passive account whose states are alike matching as in a batch, the follower read again each second, for up to three minutes, until it holds as its newest staple of the account the representative's newest, which the representative held both before and after serving its state, the follower's own state pinned to its newest staple in the same way, and serves the same state, which an account a staple touches every few seconds needs, as the follower adds a staple a minute or more after a representative does; a value alone may come round again) and with each representative in turn, and records it in the walk and the latest complete lap that missed it, so that the lap's coverage completes without a whole new lap; a walk that has completed no lap has missed none of the accounts it has not walked yet, and recheck says so. `api-diff` sends the same GET requests to the follower and to a representative, `--samples` of each stratum (300), and compares the answers once the fields `API.md` names as differing between nodes holding the same ledger are normalized: an internal failure's error ID, and a history entry's time and its staple's compression. The strata are quiet accounts of each kind that differs most from a plain account's (tokens, storage accounts, multisig accounts, accounts with certificates, and accounts with permissions as principal or entity), blocks carrying each type of operation, and the edge-case staples (`conformance/mainnet/edge-cases.jsonl.gz`) the follower holds. Every GET route of `api/openapi.json` is sampled except those whose answer describes the node that serves it, the statistics-clearing route, the representatives' weights, which move with any delegating account, and the ledger's history, which each node orders by its own vote. Requests are drawn from the follower's database within its reach, in an order `--seed` fixes (the time of the run): of each kind, at most `--samples` quiet accounts, each forming its requests (its state, head, chain, newest history entry and page from it, balances, permissions, certificates and pending blocks, at most three of each token, certificate, entity and chain block it names, and the states of it and the next account drawn), and of each type of operation at most `--samples` blocks within reach, each forming four or five (the block, its votes, its successor, the chain from it, and its idempotent key); a run of at least 300 (the done criterion) reads every held block once, in the order the database stores them, which on the main network's ledger takes some ten minutes, reads some 3.6 GB and peaks near 1.1 GiB of memory, while a smaller run, as `make parity`'s, reads some twenty thousand blocks from a page the seed fixes; each block's types of operation read from its encoding alone, and of each type the blocks the seed puts first are drawn, so a type with fewer blocks than that has every one of them drawn. The follower is asked before and after the representative, and a request whose answer the follower changed in between, once normalized, is skipped as moving. Two internal failures that name no error code of the API, an error ID alone, are no answer: such a failure has any cause, so two of them show nothing alike, and the request is skipped as unanswered. Answers alike match, with a digest of the answer once normalized, as no lag of either side makes unequal states equal, but for an answer of a value alone, a balance or a permission, which a later change may set back to what a lagging side still holds; answers apart count only when every account the answer reads, the entities a principal's permissions name included, is quiet on both sides as for the sweep, the representative's newest staples read after its answer, each representative asked about an account once a run; otherwise the request is skipped as moving. A run of at least 300 first records its plan: for each stratum, how many requests it drew, and whether they are the whole population, every request the sampler forms from the follower's data (from the accounts of the kind quiet before the hour, each naming at most three tokens, certificates, entities and blocks of its chain, or from every block within reach carrying the operation), which they are when fewer accounts or blocks than asked for are all the stratum has, and always for the edge cases. A stratum whose whole population is fewer requests than `--samples` is a census: the plan lists its every request, and the run sends each. A smaller run records no plan and claims no census. Answers that differ are sent again to every other representative, one on which an account the answer reads is not quiet giving no reading, and judged as the sweep judges a divergence: the follower's when it disagrees with most of the representatives that answered, the one compared with among them; the own of the representatives that answered apart (`representative-local`) when at least two answer as the follower and every other answer, once normalized, is given by fewer, each of them charged with it, but never for a follower that failed to answer, which no other representative's answer agrees with, nor for two pages of an account's history, where another representative may list a staple the follower lacks after one of its own, ordering the history by its own votes; otherwise `unresolved`, which fails like a divergence. A difference left to the representatives apart also records the check of the follower's balances the sweep makes, of every account the answer reads, the entities a principal's permissions list included: each against its own history, and, when the answer is that account's state, against the state served. An inconsistent check makes the divergence the follower's, and a check that could not be made, as the account moved, leaves it `unresolved`; a request whose answer reads no account, a block's, records why no check applies, and one recorded without a check counts as unresolved. A page of history the compared representative failed to serve with an internal failure is asked for again later, unless most of the answers read, that failure among them, differ from the follower's, failing or serving another page: that is the follower's divergence, and as it carries an internal failure naming no code of the API, which no later comparison settles, only its triage closes it. An answer that is a rate limit, or a server error without the API's error envelope, is no answer of the API: the request is skipped as unanswered, and from another representative gives no reading. `recheck` also sends again, in the same way, each request with an open divergence, or whose latest comparison is a divergence explained, the identical request to the representative it diverged with, each request of a standing census that has no comparison yet, and each request never compared of a route left uncovered, oldest first, to the representative last tried with it; a request skipped as moving compares once what it reads is quiet, so `recheck` is run again until the routes are covered. The report counts each request by its latest comparison. A divergence of a state that has moved on is closed by its triage: `explain` appends an `api-diff-explained` record naming the divergence by its request and the moment it was recorded, its class (`our-bug`, `upstream-version` or `operational-artifact`) and the fixing change or the section of `MAINNET.md` or `API.md` that records it, which the report lists apart (`explained`); a request whose latest comparison is a divergence explained found no answer alike, so it counts apart (`standingOnExplanation`), neither as matched, nor as a sample of its stratum, nor toward its census, and as never compared in its route's share, and `recheck` sends it again, so that a later comparison shows whether it still diverges; it refuses a divergence that is not open, a triage with no reference, and a divergence no later attempt at the request retested, by comparing it again or finding it moving, unless `--force` states why none needs to, which the record keeps (`retest`: `retested`, `forced` with that reason, or `unrecorded` for a triage recorded before triages were checked, whose reference alone states its evidence); it takes no lock.
